# Проект: автоматизации на n8n, разработка от спецификации (SDD)

Источник правды — этот репозиторий. n8n — среда исполнения, куда воркфлоу деплоятся импортом.

## Где что лежит

- `openspec/specs/<воркфлоу>/spec.md` — актуальная спека каждого воркфлоу. Одна capability = один воркфлоу n8n.
- `openspec/changes/<change>/` — предложения изменений: proposal, дельта спеки, design, tasks.
- `openspec/config.yaml` — конституция проекта и правила артефактов. Читать перед любой работой со спеками.
- `openspec/schemas/n8n-workflow/` — схема и шаблоны артефактов под n8n. Кастомизация только здесь и в config.yaml, файлы в `.claude/` генерируются командой `openspec update`.
- `workflows/<воркфлоу>.json` — нормализованный экспорт из n8n. Руками не редактировать.
- `tests/<воркфлоу>/case-NN.{input,expected}.json` — тест-кейсы, по одному на Scenario спеки.
- `scripts/` — экспорт, импорт, нормализация, проверка конституции.

## Цикл работы

1. `/opsx:propose "<что меняем>"` — создаёт change с proposal, дельтой спеки, design и tasks. Только планирование.
2. Ревью артефактов человеком. Спека и design правятся до сборки.
3. `/opsx:apply` — сборка воркфлоу в n8n через n8n MCP или REST API, прогон тест-кейсов, `npm run export -- <воркфлоу>`, `npm run check -- <воркфлоу>`.
4. Коммит: спека и `workflows/<воркфлоу>.json` всегда в одном коммите.
5. `/opsx:archive` — дельта вливается в `openspec/specs/`.
6. Включение: воркфлоу активируется в n8n только после прохождения тестов и с согласия пользователя.

Стенд один — рабочий инстанс из `.env`, отдельного тестового нет. Отсюда правила безопасности в разделе «Правила для агента».

## Команды

```
npm install                       # ставит openspec локально
npm run export -- <воркфлоу>      # n8n → workflows/<воркфлоу>.json (с нормализацией)
npm run import -- <воркфлоу>      # workflows/<воркфлоу>.json → n8n
npm run check -- <воркфлоу>       # проверка конституции (Sticky Note, Error Workflow, Code ≤ 50 строк, секреты, тесты)
npm run validate                  # openspec validate --all --strict
```

Доступ к n8n: скопировать `.env.example` в `.env`, заполнить `N8N_API_URL` и `N8N_API_KEY`. Файл `.env` в git не попадает.

## n8n MCP

Подключён через `.mcp.json` → `scripts/n8n-mcp.sh` → пакет `n8n-mcp` (запускается через npx, ключи берёт из `.env`).
При первом открытии проекта Claude Code спросит разрешение на MCP-сервер из репозитория — согласиться.
Без `.env` сервер работает только как справочник по нодам.

Как использовать в цикле apply:
- до сборки: `search_nodes`, `get_node` — параметры нод; `validate_node` — проверка конфигурации ноды
- сборка: `n8n_create_workflow`, правки — `n8n_update_partial_workflow` (диффом, не полной заменой)
- проверка: `n8n_validate_workflow`, затем `n8n_test_workflow` с данными из `tests/<воркфлоу>/case-NN.input.json`
- экспорт в репозиторий всё равно через `npm run export -- <воркфлоу>`, а не через MCP: только скрипт даёт нормализацию
- `n8n_delete_workflow` и `n8n_manage_credentials` без явной просьбы пользователя не вызывать

## Правила для агента

- Спека описывает поведение, не узлы. Названия нод и выражения n8n — только в design.md.
- Секреты в любом файле репозитория — стоп и сообщить пользователю.
- Воркфлоу собирать через n8n MCP или REST API, не правкой JSON руками.
- Расхождение между спекой и тем, что уже стоит в n8n, — вопрос к пользователю, а не молчаливый выбор.
- Стенд один и рабочий. Новый воркфлоу создаётся выключенным. Активировать — только после тестов и согласия пользователя.
- Правка уже активного воркфлоу — только с явного согласия пользователя на конкретное изменение.
- Тесты, которые пишут во внешние системы (CRM, Notion, почта, мессенджеры), — только на тестовых записях или через pin data. Если так нельзя — спросить пользователя до прогона.
